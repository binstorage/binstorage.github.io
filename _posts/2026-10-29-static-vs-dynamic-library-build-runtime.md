`.framework`는 파일이 아니라 **디렉토리(번들)**다. 그 안에 헤더와 바이너리가 들어있고, 소스 코드는 없다. 이 글에서는 이 구조가 빌드와 런타임에서 어떻게 사용되는지, 정적 라이브러리와 동적 라이브러리의 차이를 흐름 중심으로 정리한다.

---

## Framework 디렉토리 구조

```
openssl.framework/
├── openssl          ← 실제 바이너리 (Mach-O)
├── Headers/         ← 헤더 파일 (.h)
│   └── *.h
├── Modules/         ← 모듈맵 (있을 경우)
└── Info.plist       ← 메타데이터
```

- **헤더(.h)**: 함수 선언(인터페이스). 컴파일러에게 "이런 함수가 존재한다"를 알려주는 역할.
- **바이너리**: 함수의 실제 구현이 컴파일된 기계어 코드.

`file` 명령으로 바이너리 타입을 확인할 수 있다.

```bash
file openssl.framework/openssl

# 정적 라이브러리:
# current ar archive

# 동적 라이브러리:
# Mach-O 64-bit dynamically linked shared library
```

---

## 정적 라이브러리 빌드·런타임 흐름

정적 라이브러리(ar archive)는 미리 컴파일된 `.o` 파일들의 묶음이다.

```
┌─────────────────────────────────────────────────────────┐
│                      빌드 타임                            │
│                                                         │
│  ① 컴파일                                               │
│  ┌──────────┐    ┌─────────────┐                        │
│  │ 내 코드   │ + │ Headers/*.h │ → .o 파일 생성           │
│  │ (.m/.c)  │    │ (함수 선언)  │   (함수 호출부는         │
│  └──────────┘    └─────────────┘    심볼 참조만 기록)      │
│                                                         │
│  ② 링크                                                 │
│  ┌──────────┐    ┌──────────────────┐                   │
│  │ 내 .o    │ + │ openssl 바이너리   │ → 최종 .app 바이너리 │
│  │ 파일들   │    │ (ar archive)     │                    │
│  └──────────┘    └──────────────────┘                   │
│                  라이브러리의 기계어 코드를                  │
│                  최종 바이너리에 복사·병합                   │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                       런타임                              │
│                                                         │
│  [ .app 바이너리 ] ── 그냥 실행                            │
│                                                         │
│  라이브러리 코드가 이미 바이너리 안에 포함되어 있으므로       │
│  별도 로딩 과정 없이 직접 함수 호출                         │
│                                                         │
│  → .framework 파일은 런타임에 필요 없음                    │
└─────────────────────────────────────────────────────────┘
```

빌드가 끝나면 라이브러리의 기계어 코드가 앱 바이너리에 **병합**된다. 런타임에 framework 파일은 필요하지 않다.

---

## 동적 라이브러리 빌드·런타임 흐름

동적 라이브러리(dylib)는 링크 시 코드를 복사하지 않고, 런타임에 별도로 로드한다.

```
┌─────────────────────────────────────────────────────────┐
│                      빌드 타임                            │
│                                                         │
│  ① 컴파일                                               │
│  ┌──────────┐    ┌─────────────┐                        │
│  │ 내 코드   │ + │ Headers/*.h │ → .o 파일 생성           │
│  │ (.m/.c)  │    │ (함수 선언)  │   (정적과 동일)          │
│  └──────────┘    └─────────────┘                        │
│                                                         │
│  ② 링크                                                 │
│  ┌──────────┐    ┌──────────────────┐                   │
│  │ 내 .o    │ + │ openssl 바이너리   │ → 최종 .app 바이너리 │
│  │ 파일들   │    │ (dylib)          │                    │
│  └──────────┘    └──────────────────┘                   │
│                  코드는 복사하지 않음                       │
│                  "SSL_connect는 openssl.framework에 있다" │
│                  라는 참조 정보(LC_LOAD_DYLIB)만 기록       │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                       런타임                              │
│                                                         │
│  ① 앱 실행 시작                                          │
│  [ .app 바이너리 ] → dyld(동적 링커) 가동                  │
│                                                         │
│  ② dyld가 LC_LOAD_DYLIB 목록을 읽음                      │
│     "openssl.framework/openssl 을 로드해야 한다"           │
│                                                         │
│  ③ @rpath 등 경로 변수를 해석하여 .framework 파일 탐색      │
│     MyApp.app/Frameworks/openssl.framework/openssl       │
│                                                         │
│  ④ 해당 dylib를 메모리에 매핑 (mmap)                      │
│                                                         │
│  ⑤ 심볼 바인딩 — 내 코드의 SSL_connect 호출 주소를         │
│     로드된 라이브러리의 실제 함수 주소로 연결                │
│                                                         │
│  ⑥ 정상 실행 / 로드 실패 시 크래시                         │
│     "Library not loaded … Reason: image not found"       │
│                                                         │
│  → .framework 파일이 런타임에 반드시 존재해야 함            │
└─────────────────────────────────────────────────────────┘
```

동적 라이브러리는 빌드 시 **참조만 기록**하고, 런타임에 dyld가 실제 라이브러리를 **메모리에 로드**한 뒤 심볼 주소를 연결한다. Framework 파일이 앱 번들에 포함되어야 하며, 누락 시 크래시한다.

---

## 앱 번들 구조 비교

```
정적 라이브러리 사용 시:             동적 라이브러리 사용 시:

MyApp.app/                         MyApp.app/
├── MyApp  (크기 큼, 코드 포함)      ├── MyApp  (크기 작음, 참조만)
└── Info.plist                     ├── Info.plist
                                   └── Frameworks/
                                       └── openssl.framework/
                                           └── openssl  ← 런타임 필수
```

## 비교 정리

### 빌드 타임

| 단계 | 정적 라이브러리 | 동적 라이브러리 |
|------|---------------|---------------|
| 컴파일 | 헤더로 함수 선언 확인 | 동일 |
| 링크 | 기계어 코드를 최종 바이너리에 **복사·병합** | 심볼 **참조만 기록** (LC_LOAD_DYLIB) |
| 결과물 | .app 바이너리 하나 | .app + .framework 별도 파일 |

### 런타임

| 항목 | 정적 라이브러리 | 동적 라이브러리 |
|------|---------------|---------------|
| 시작 시 | 그냥 실행 | dyld가 .framework를 메모리에 로드 |
| 함수 호출 | 같은 바이너리 안에서 직접 점프 | 로드된 라이브러리의 주소로 점프 |
| .framework 필요 여부 | 빌드 후 **불필요** | **반드시 앱과 함께 배포** |
| 앱 시작 속도 | 로딩 오버헤드 없음 | dyld 로딩 시간 추가 |
| 누락 시 | 해당 없음 | 크래시 (image not found) |

### 장단점

| 항목 | 정적 라이브러리 | 동적 라이브러리 |
|------|---------------|---------------|
| 배포 | 간단 (.app 하나) | .framework 포함 필수 |
| 앱 바이너리 크기 | 큼 (코드 포함) | 작음 (참조만) |
| 메모리 공유 | 불가 (프로세스마다 복사본) | 가능 (여러 프로세스가 공유) |
| 라이브러리 교체 | 앱 전체 재빌드 필요 | .framework만 교체 가능 |
| 런타임 안정성 | 누락 위험 없음 | 로드 실패 가능성 존재 |

---

## 헤더와 바이너리의 역할

| 구성 요소 | 역할 | 필요 시점 |
|-----------|------|-----------|
| 헤더 (.h) | 함수 선언 (인터페이스 정의) | 컴파일 타임 |
| 바이너리 (정적) | 함수 구현 (기계어 코드), 최종 바이너리에 병합됨 | 링크 타임 |
| 바이너리 (동적) | 함수 구현 (기계어 코드), 런타임에 별도 로드됨 | 링크 타임 + 런타임 |

소스 코드가 없어도 동작하는 이유는, 바이너리 안에 이미 **컴파일된 기계어 코드**가 들어있기 때문이다. 헤더는 컴파일러에게 인터페이스를 알려주고, 링커가 바이너리에서 실제 구현을 찾아 연결한다.
