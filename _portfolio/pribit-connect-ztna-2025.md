## 주요 기능 및 구현

### 네트워크 통제 (macOS 기준)

- **판단**: 새 연결마다 목적지 IP·Port·프로토콜·애플리케이션(프로세스) 정보를 뽑아 패킷 제어 판단 모듈로 허용 여부를 결정합니다. Apple 시스템 구성요소의 연결은 판단에서 제외합니다.
- **기본 차단**: 서버 정책에 등록된 목적지 IP·Port·애플리케이션에 맞는 연결만 허용하고 나머지는 차단합니다.
- **정책 요청**: 정책에 없는 연결은 서버에 정책을 요청합니다. 같은 요청은 큐에서 걸러 한 번만 보내고 순서대로 처리합니다.
- **제어 영역 외 차단**: 정책이 켜지면 제어 영역(라우팅 대역)에 속하지 않는 연결을 모두 차단합니다.
- **선접속 후인증**: 선접속 대역의 연결은 먼저 허용한 뒤 서버에 정책을 확인하고, 정책이 없으면 차단 테이블에 등록해 이후 패킷을 차단합니다. VPN 대역은 터널에서 이미 열린 세션까지 끊습니다.
- **상태 관리**: 판단 결과를 허용·차단·나중에 차단될 수 있는 허용으로 나누고, 마지막은 따로 추적해 인증 결과가 나오면 연결을 끊습니다.
- **iOS**: 터널에서 읽은 패킷에는 애플리케이션 정보가 없어, 애플리케이션 구분 없이 목적지 IP·Port로만 판단합니다.

### 스크린 워터마크 (macOS)

- **목적**: 정책이 켜지면 모든 모니터 위에 사용자 정보와 시간을 반투명하게 표시해, 화면 촬영·유출 시 누가 언제 본 화면인지 드러나게 합니다.
- **표시**: 모니터마다 테두리 없는 투명 창을 만들어 다른 창보다 위에 띄웁니다. 마우스 클릭은 아래 창으로 그대로 통과시키고, 모든 데스크톱 공간(Spaces)과 전체 화면 앱 위에도 표시합니다.
- **정책 반영**: 문구, 투명도, 글자 크기, 각도, 위치, 시간 표시·형식·위치, 가로·세로 간격을 서버 정책에서 받아 SwiftUI 화면에 적용합니다. 확장형(화면 전체에 하나)과 패턴형(격자 반복)을 지원합니다.
- **시간 갱신**: 1초마다 현재 시각을 다시 그려 캡처 시각과 표시 시각을 맞춥니다.
- **대응**: 멀티 윈도우 사용 시 워터마크가 사라지는 문제, 모니터 연결·해제 시 창 재생성

### 화면 캡처 방지 (macOS)

- **목적**: 정책이 켜지면 화면 캡처 저장과 PrintScreen 사용을 막습니다.
- **구현**: 모니터마다 옅은 투명 오버레이 창을 최상위 레벨에 띄우고, 화면의 창 목록을 조회해 각 창 영역을 캡처 제외 영역으로 지정합니다. 캡처하면 창 내용 대신 가려진 이미지가 저장됩니다.
- **연동**: 공개 API로는 다른 창을 캡처에서 제외할 수 없어, CoreGraphics 내부 함수를 Objective-C로 연동했습니다.
- **감지**: 시스템의 스크린샷 완료 알림으로 캡처 시도를 감지합니다.

### 1. iOS 선접속 후인증

- **설명**: 먼저 연결된 세션을, 이후 인증 결과에 따라 끊을 수 있어야 했습니다.
- **문제**: NEFilterDataProvider는 **이미 허용한 세션을 끊을 수 없는** 제한이 있습니다.
- **구현**: 세션 차단을 NEPacketTunnelProvider 쪽에서 처리하도록 바꿔, 선접속된 세션을 끊을 수 있게 했습니다. [확인 필요 — 터널에서 차단한 구체적인 방식]

### 2. 추가 인증 (TOTP, SMS)

- **설명**: 강화된 인증 타입으로 TOTP와 SMS(URL) 인증을 추가했습니다.

### 3. 고객사 이슈 대응 및 코드 형상 관리

- **고객사**: 삼양식품, 한화, 포스코인터내셔널, 팬택씨앤아이, 에이치와이, 중앙백신연구소, 핵융합에너지연구원, 화승코퍼레이션 등 8개 이상 고객사 이슈 대응
- **기존**: 각자 하나의 브랜치에서 Push·머지를 반복했습니다.
- **문제**: 배포본과 개발 중인 코드가 한 브랜치에 섞여 어떤 커밋이 어느 배포에 들어갔는지 추적하기 어렵고, 긴급 수정 시 미완성 기능까지 함께 배포될 위험이 있었습니다. 서로 머지가 얽혀 히스토리를 읽기도 어려웠습니다.
- **제안**: 사수에게 Git Flow 기반 브랜치 전략을 건의해 도입했습니다. 배포 브랜치(packetgo_til_branch)에서 dev를, dev에서 기능·이슈별 브랜치를 나누고, 긴급 수정은 hotfix 브랜치로 분리합니다.
- **결과**: 브랜치마다 역할이 나뉘어 커밋 그래프가 읽기 쉬워졌고, 긴급 수정을 개발 중인 코드와 분리해 반영할 수 있게 됐습니다.
- **운영**: 고객사 이슈는 Jira로 접수·분배하고, 2인 팀이라 별도 PR 없이 Push하면 사수와 가볍고 짧은 리뷰 후 머지합니다.

## 회고

- **배운 점**: Network Extension의 Provider마다 할 수 있는 일과 제한이 분명히 다르다는 것을 배웠습니다. 요구사항을 받으면 먼저 어느 Provider에서 처리할 수 있는지 확인하는 습관이 생겼습니다.
- **아쉬운 점**: 운영 중인 제품을 유지보수하면서 구조적 한계(테스트 불가, 사이드 이펙트)를 계속 느꼈고, 이 경험이 PacketGo OS 아키텍처 설계로 이어졌습니다.
